# System Design and Architecture
**Product:** Personal Finance Manager (Android)
**Version:** 1.0 — MVP

---

## 1. Architectural drivers

Four requirements dominate every decision in this document. Where they conflict with convenience, they win.

1. **≤ 800 ms cold start on a Cortex-A53** — rules out heavyweight frameworks, annotation-processor-driven DI graphs constructed at startup, and reflection-based serialisation
2. **≤ 6 MB APK** — rules out cross-platform runtimes, charting libraries, and analytics SDKs
3. **Offline-only** — removes the network layer, sync engine, auth, and conflict resolution entirely
4. **Zero data loss** — writes commit before the UI acknowledges them; every aggregate is reconstructible from the ledger

A useful way to read the rest of this document: almost every choice below is subtractive. The architecture is defined more by what it omits than by what it contains.

## 2. Technology selection

| Layer | Choice | Rationale |
|---|---|---|
| Language | Kotlin | Platform default, no runtime overhead over Java, coroutines fit the threading model |
| UI toolkit | Jetpack Compose | See discussion below |
| Persistence | Room over SQLite | Compile-time query verification, zero native dependencies, SQLite is already on the device |
| Async | Coroutines + Flow | Structured concurrency, first-class Room integration |
| DI | Hand-rolled container | See discussion below |
| Background work | WorkManager | Only for recurring-rule evaluation; the app requires no other background execution |
| Preferences | Room `app_meta` table | Avoids pulling in DataStore for a handful of keys |
| Charts | Custom Compose Canvas | See discussion below |
| Serialisation | `kotlinx.serialization` | Compile-time, no reflection; ~100 KB |
| Build | Gradle KTS, R8 full mode | |

### 2.1 Why native, not Flutter or React Native

This is the decision with the largest effect on the size and startup budgets. A Flutter release APK starts around 7–8 MB before any application code, because the engine ships with the app; React Native carries both a JS runtime and a bridge, plus JS bundle parsing at every cold start. Either would consume the entire 6 MB budget before the first screen exists, and both add a startup cost that is structurally difficult to remove.

The counter-argument — cross-platform reach — does not apply, because iOS is explicitly out of scope. There is nothing to trade for.

### 2.2 Why Compose, with a caveat

Compose adds roughly 1.5–2.5 MB after R8 shrinking, which is real against a 6 MB ceiling. It is chosen anyway because the alternative — XML views with `findViewById` or view binding — costs significantly more code for the dynamic, state-driven lists this app is made of, and Compose's recomposition model makes the "budget bar updates the instant an expense saves" requirement almost free.

The caveat is that Compose's historical weakness is exactly this app's target: startup on low-end devices. Three mitigations are mandatory, not optional:

- **Baseline Profiles**, generated by the Macrobenchmark module and shipped in the release build. On low-end hardware these routinely cut Compose cold start by 20–30% by avoiding interpretation of hot composition paths.
- **A single Activity, no Fragments**, so there is one inflation pass.
- **`R8` full mode with Compose-aware rules**, and no `@Preview` code reachable from release.

If M1 benchmarks on the reference device miss the 800 ms target after these mitigations, the fallback is XML views for the two hottest screens only — entry and ledger — keeping Compose elsewhere. That decision point belongs at M1, with numbers, not now.

### 2.3 Why hand-rolled dependency injection

Hilt is the conventional answer and the wrong one here. It brings an annotation processor, generated component classes, and a graph built during `Application.onCreate` — directly on the cold-start path. For an application with roughly a dozen injectable types, a plain container is smaller, faster, and fully comprehensible:

```kotlin
class AppContainer(context: Context) {
    val db: AppDatabase by lazy { AppDatabase.build(context) }
    val expenseRepo: ExpenseRepository by lazy { ExpenseRepository(db.expenseDao(), clock) }
    val incomeRepo: IncomeRepository by lazy { IncomeRepository(db.incomeDao(), clock) }
    val budgetRepo: BudgetRepository by lazy { BudgetRepository(db.budgetDao(), clock) }
    val clock: Clock = Clock.systemDefaultZone()
}
```

Every dependency is `by lazy`, so nothing — including opening the database — happens until the first screen actually needs it. `Application.onCreate` stays close to empty, which is the single most effective cold-start intervention available.

The honest trade-off: hand-rolled DI scales poorly past a certain size. At the point where this app has fifty injectable types it will want a framework. It will not reach that point as an MVP.

### 2.4 Why no charting library

MPAndroidChart is roughly 1 MB and brings an entire rendering framework for what this product needs: one line chart and one bar series. Both are a few dozen lines of Compose `Canvas` — `drawPath` for the trend, `drawRect` for the bars, `drawLine` for the budget reference. The library would consume a sixth of the size budget to save a day of work, and it would render more slowly than purpose-built drawing because it carries generality this app does not use.

### 2.5 Dependency budget

Every runtime dependency is listed and justified. NFR-SIZE-04 requires written rationale for anything over 300 KB.

| Dependency | Approx. size | Justification |
|---|---|---|
| Kotlin stdlib | ~1.0 MB | Unavoidable |
| Compose runtime + UI + Material3 | ~2.0 MB | §2.2; Material3 restricted to used components |
| Room runtime | ~250 KB | Query verification, migration tooling |
| Coroutines | ~350 KB | Threading model |
| kotlinx.serialization | ~100 KB | Export/import without reflection |
| WorkManager | ~400 KB | P1 only — excluded from the M1–M4 builds |
| **Excluded deliberately** | | Hilt, Firebase, any analytics SDK, any charting library, Gson/Moshi, Retrofit/OkHttp, image loading |

Excluding OkHttp deserves a note: it is the reflexive dependency in almost every Android project, and this app has no use for it at all. Its absence is a consequence of not declaring the `INTERNET` permission, and it is worth several hundred kilobytes.

## 3. Layered structure

```
┌─────────────────────────────────────────────────────┐
│  UI            Compose screens, single Activity     │
│                stateless, render from UiState       │
├─────────────────────────────────────────────────────┤
│  Presentation  ViewModels, StateFlow<UiState>       │
│                survive rotation and process death   │
├─────────────────────────────────────────────────────┤
│  Domain        Pure Kotlin. Budget states, safe-to- │
│                spend, projections, deltas.          │
│                No Android imports. JVM-testable.    │
├─────────────────────────────────────────────────────┤
│  Data          Repositories. Coordinate DAOs,       │
│                enforce invariants, own transactions │
├─────────────────────────────────────────────────────┤
│  Persistence   Room DAOs, entities, migrations,     │
│                triggers → SQLite (WAL)              │
└─────────────────────────────────────────────────────┘
```

Dependencies point strictly downward. The domain layer having no Android dependency is what makes NFR-MAIN-01 and the 80% coverage target achievable — budget state transitions and burn-rate projections are the logic most likely to be wrong, and they are testable in milliseconds on the JVM with no emulator.

### 3.1 Package layout

A single Gradle module, packaged by feature:

```
com.app.finance
├── MainActivity.kt
├── FinanceApp.kt              // Application; deliberately near-empty
├── di/AppContainer.kt
├── core/
│   ├── money/Money.kt         // inline value class over Long paisa
│   ├── time/Period.kt         // YYYYMM arithmetic, epoch-day conversion
│   └── text/NameKey.kt        // locale-aware normalisation
├── data/
│   ├── db/{AppDatabase, migrations, dao/, entity/}
│   └── repo/{Expense, Income, Budget, Category, Backup}Repository.kt
├── domain/
│   ├── model/                 // Money, BudgetStatus, CategoryNode
│   └── usecase/               // SafeToSpend, BurnRate, CategoryDelta, StableCoverage
└── ui/
    ├── theme/
    ├── common/                // AmountField, CategoryPicker, BudgetBar, charts
    └── feature/{dashboard, entry, ledger, income, budget, category, settings}/
```

**Single module, not multi-module.** Multi-module builds improve incremental compile time on large teams and enforce boundaries mechanically. For one developer and roughly 8,000 lines, they add Gradle configuration overhead that exceeds the benefit. Package boundaries plus a lint rule forbidding `android.*` imports inside `domain/` achieves the same discipline at a fraction of the cost. Split when build times actually hurt, not before.

## 4. Core type decisions

### 4.1 Money

```kotlin
@JvmInline
value class Money(val paisa: Long) {
    operator fun plus(o: Money) = Money(paisa + o.paisa)
    operator fun minus(o: Money) = Money(paisa - o.paisa)
    fun format(): String = /* ৳ with grouping, two decimals */
    companion object { val ZERO = Money(0) }
}
```

An inline value class compiles to a bare `Long` at runtime — full type safety with no allocation. This matters on two fronts: it makes it a compile error to add a `Money` to a raw number, and it costs nothing in a list rendering hundreds of amounts.

`Double` for money is prohibited throughout. Not discouraged — prohibited, and enforced by a lint rule, because a rounding bug in a ledger is silent and discovered months later.

### 4.2 Period

```kotlin
@JvmInline
value class Period(val ym: Int) {          // 202608
    fun prev(): Period
    fun next(): Period
    fun minusMonths(n: Int): Period
    fun dayRange(): LongRange              // epoch-day bounds
    fun daysInMonth(): Int
}
```

Period arithmetic is the second most common source of bugs after money — particularly December→January rollover and the 31st in a 30-day month. Centralising it in one value class with exhaustive unit tests, rather than scattering `Calendar` calls, removes an entire bug class.

## 5. Data flow

### 5.1 Write path — the expense entry hot path

```
User taps Save
   ↓
ViewModel.save(amount, categoryId, date, method, note)
   ↓  viewModelScope, Dispatchers.IO
ExpenseRepository.insert(...)
   ├─ validate: amount ≠ 0, category is leaf and not archived
   ├─ derive period_ym from spent_on
   ├─ assign UUID, created_at, updated_at
   └─ single transaction:
        INSERT INTO expense       ─── trigger ──▶ rollup_expense_month
        UPDATE app_meta (last-used category, method)
   ↓
Room invalidation tracker fires
   ↓
All observing Flows re-emit  →  dashboard, ledger, budget bars update
   ↓
ViewModel emits Saved; UI shows snackbar with Undo
```

Two properties fall out of this design rather than being coded:

**Aggregates cannot drift.** The rollup update is inside the same transaction as the insert, performed by a database trigger. There is no code path — including bulk import, undo, and future features — that can write an expense without updating its aggregate.

**No manual refresh anywhere.** Room's invalidation tracker notifies every `Flow` observing an affected table. The dashboard does not subscribe to a "expense added" event; it observes a query and re-emits. This eliminates the whole category of bugs where one screen updates and another shows stale numbers.

### 5.2 Read path — the dashboard

```
DashboardViewModel
   ├── observe rollup_expense_month  (period)   ─┐
   ├── observe rollup_income_month   (period)   ─┤ combine()
   ├── observe budget                (period)   ─┤   ↓
   └── observe category tree                    ─┘ pure domain functions
                                                    ├ SafeToSpend
                                                    ├ BurnRateProjection
                                                    ├ CategoryDelta
                                                    └ StableCoverage
                                                        ↓
                                                 StateFlow<DashboardUiState>
```

The database returns small aggregate rows; all derived metrics are computed by pure functions over those rows. No metric is computed in SQL beyond summation, which keeps the interesting logic unit-testable and keeps the queries index-friendly.

`stateIn(SharingStarted.WhileSubscribed(5_000))` retains state across configuration changes without re-querying, and releases it shortly after the screen goes away.

### 5.3 Threading

| Work | Thread |
|---|---|
| Composition, layout, draw | Main |
| All DAO access | `Dispatchers.IO` via suspend functions or Flow |
| Domain calculations | Whatever `combine` runs on, off-main by construction |
| Export / import | `Dispatchers.IO`, foreground with progress |

StrictMode in debug builds enables `detectDiskReads`, `detectDiskWrites`, and `penaltyDeath`, making any accidental main-thread database access a crash during development rather than a jank report from a user (NFR-PERF-09).

## 6. Startup design

Cold start is the tightest budget in the specification. The sequence is designed backwards from 800 ms.

```
Process start
   ↓
FinanceApp.onCreate()          ← target < 10 ms
   └─ construct AppContainer   ← all fields lazy; NO database open
   ↓
MainActivity.onCreate()
   └─ setContent { AppTheme { NavHost(start = Dashboard) } }
   ↓
Dashboard composes with empty/skeleton state    ← first frame here
   ↓
Database opens on first query, off-main
   └─ first-run only: create schema + seed inside one transaction
   ↓
Flows emit; dashboard populates
```

The decisive property is that **the first frame does not wait on the database.** The dashboard renders its skeleton immediately and fills in when data arrives, typically within one or two frames. An architecture that blocks the first frame on opening SQLite, running migrations, and executing four queries cannot hit 800 ms on eMMC storage regardless of how well the rest is written.

Additional measures:

- **Baseline Profile** generated by Macrobenchmark, covering app startup and the dashboard/ledger/entry paths
- **No `ContentProvider`-based library initialisers** — `androidx.startup` is disabled in the manifest, since each auto-initialised provider runs before the first Activity
- **`android:allowBackup="false"`**, which also avoids backup-agent work at install
- **No WorkManager in the M1–M4 builds** — it initialises via a `ContentProvider` by default; when introduced for recurring rules at P1, on-demand initialisation is used instead

## 7. Screen inventory

| Screen | Purpose | Notes |
|---|---|---|
| Dashboard | Safe-to-spend, net position, budget bars, alerts, top deltas | Entry point; the 300 ms target applies here |
| Quick Add (bottom sheet) | Amount → category → save | Reachable in one tap from every primary screen |
| Ledger | Paged, grouped by day, filter + search | Keyset pagination |
| Income | Entries, source breakdown, period and range totals, trend | |
| Income Source Editor | Create, rename, set kind, archive | |
| Budget | Per-period limits, copy-from-last-month | |
| Category Manager | Two-level tree, create/rename/reorder/archive | |
| Reports | Custom date range, fixed/variable split, top expenses | Ledger-backed rather than rollup-backed |
| Settings | Export, import, rebuild aggregates, delete all data, theme | |

Navigation is a single `NavHost` with a bottom bar of four destinations — Dashboard, Ledger, Income, Budget — and a centre FAB for Quick Add. Everything else is a detail route or a bottom sheet.

The FAB placement is a usability requirement, not decoration: NFR-USE-06 requires one-handed operation on a 5-inch display, so the single most frequent action must sit in the thumb arc.

## 8. Error handling and integrity

| Concern | Handling |
|---|---|
| Validation failure | Field-level error in the entry form; save disabled until resolved |
| Constraint violation | Repository maps `SQLiteConstraintException` to a typed domain error with an actionable message; never a raw exception surfaced to the user |
| Migration failure | Release builds never fall back to destructive migration. Failure surfaces a recovery screen offering export of the raw database file |
| Import failure | Whole import runs in one transaction; any failure rolls back leaving the prior state untouched (FR-DAT-04, NFR-REL-04) |
| Rollup drift | Debug-build startup assertion compares rollups against live aggregates; user-invocable rebuild in Settings |
| Process death | `SavedStateHandle` restores the current period and in-progress entry form |

**No crash reporting SDK.** NFR-SEC-02 forbids it, and a single-user app has no fleet to monitor. Unhandled exceptions are written to an app-private log file that the user can attach to a manual bug report if they choose.

## 9. Testing strategy

| Level | Scope | Target |
|---|---|---|
| Unit (JVM) | Domain use cases, `Money`, `Period`, name-key normalisation | ≥ 90% on `domain/` and `core/` |
| DAO (instrumented, in-memory Room) | Every query, all triggers, constraint behaviour | 100% of DAO methods |
| Migration | Populated DB from each prior version | Every migration |
| Macrobenchmark | Cold start, dashboard render, ledger scroll | Asserted per release candidate |
| Manual regression | Full pass with StrictMode enabled | Each milestone |

The DAO tests are the highest-value suite in the project, because the trigger-maintained rollups are the only place where the same fact is stored twice. The nineteen assertions recorded in the database design document are the starting point for that suite and should be ported directly into instrumented tests.

Period arithmetic deserves explicit edge-case tests: December→January rollover, leap-year February, anchor day 31 in a 30-day month, and the last day of a month for safe-to-spend division.

## 10. Build configuration

```kotlin
release {
    isMinifyEnabled = true
    isShrinkResources = true
    proguardFiles(getDefaultProguardFile("proguard-android-optimize.txt"), "proguard-rules.pro")
}
```

- **R8 full mode** enabled in `gradle.properties`
- **Resource shrinking** on, with unused Material3 resources removed
- **App Bundle** for distribution, so density and language splits are served per device
- **Language resources restricted** to shipped locales, which removes a surprising amount of AndroidX translation weight
- **Debug symbols stripped**; no native code to strip beyond the platform
- **Single dex** — if the method count approaches the limit, the correct response is removing a dependency, not enabling multidex, which adds startup cost on API 26 devices

Size and startup are tracked as CI-visible metrics on every release candidate. A pull request that increases APK size by more than 200 KB requires the same written justification as a new dependency, because size regressions arrive in small increments and are never noticed individually.

## 11. Extension path

The v1 architecture is deliberately server-free, which raises the question of whether it forecloses sync later. It does not, and the reason is `uuid` plus `updated_at` on every entity — the two fields a sync engine needs.

| Future capability | What it requires | Whether v1 blocks it |
|---|---|---|
| Cloud backup | Upload the export JSON; add `INTERNET` | No — export already produces the artifact |
| Multi-device sync | Sync engine, conflict resolution, tombstone table for deletes | Partly — a `deleted_at` soft-delete column would need adding by migration |
| SMS auto-import | `RECEIVE_SMS`, per-bank parsers, a staging table of unconfirmed entries | No — the pending-status mechanism built for recurring rules is exactly the right landing place |
| Multi-currency | Currency column, rate table, base-currency reporting | Partly — every stored amount would need a currency association |
| Accounts and balances | Account entity, transfer transaction type, opening balances | Partly — transfers must be a distinct type so that moving cash to bKash is not counted as spending |

The one genuine debt is soft deletes. If multi-device sync is ever likely, adding `deleted_at` in v1 costs almost nothing now and is awkward to retrofit once devices hold divergent histories. It is left out of the MVP because sync is not on the roadmap, but it is the first thing to reconsider if that changes.

## 12. Summary of consequential decisions

| Decision | Alternative rejected | Why |
|---|---|---|
| Native Kotlin | Flutter / React Native | Engine size alone exceeds the APK budget; no iOS target to justify it |
| Trigger-maintained rollups | Aggregate on read | Measured 5× faster at 20k rows, 77× at 100k; flat rather than linear |
| `INTEGER` paisa | `REAL` / `BigDecimal` | Exactness; no allocation in list rendering |
| `period_ym` denormalised | `strftime()` on query | Turns every monthly filter into an indexed equality test |
| Hand-rolled DI | Hilt | No annotation processor, no graph construction on the startup path |
| Compose Canvas charts | MPAndroidChart | ~1 MB for two chart types the app can draw in 50 lines |
| Single module | Multi-module | Gradle overhead exceeds the benefit at one developer, ~8k lines |
| No `INTERNET` permission | Standard manifest | Makes the privacy claim structural rather than a promise |
| Archive, never delete | Cascade delete | Deleting a category silently rewrites historical reports |
| Two-level category depth | Arbitrary nesting | Recursive rollups on every read for no real benefit at this scale |
